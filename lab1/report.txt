# Stack Buffer Overflow in rlottie bufferToRle → Remote Code Execution via Telegram Sticker

## Attack Surface
Telegram Desktop animated sticker (.tgs) rendering via bundled rlottie library.

## Vulnerability Summary
A stack buffer overflow in `bufferToRle()` (rlottie/src/vector/vrle.cpp:577) allows
a crafted `.tgs` animated sticker to overwrite the saved return address on the stack,
achieving arbitrary code execution. The attack is zero-click: stickers auto-play on
receipt with default Telegram settings.

## Root Cause
`bufferToRle()` accepts no output-capacity parameter and performs no bounds check.
It writes `VRle::Span` entries (8 bytes each) sequentially into a caller-provided
pointer. Both callers (`rleOpGeneric` at line 616 and `rleSubstractWithRle` at line
681) allocate a fixed `std::array<VRle::Span, 256>` (2048 bytes) on the stack.

When the 1024-byte coverage buffer contains alternating non-zero/zero values (every
pixel), `bufferToRle` emits up to 512 spans — double the buffer capacity. The excess
256 spans (2048 bytes) overwrite adjacent stack memory including:
  - Local variables between temp[] and the frame boundary
  - The saved RBP (frame pointer)
  - The saved RIP (return address)
  - Caller stack frames (if overflow is large enough)

## Telegram Validation Bypass

Telegram servers validate that .tgs stickers declare w=512, h=512 and are <64KB
gzipped. The PoC sticker uses:
  - 512×512 declared canvas (passes dimension check)
  - 2× layer scale transform (ks.s = [200, 200, 100])
  - Mask paths rasterized at 1024px effective width

Telegram validates declared canvas dimensions but does NOT validate that layer
transforms keep rendered content within canvas bounds. The mask rasterizer
receives no clip rect (lottieitem.cpp:208), so the 2× scale doubles the
effective rendering width to 1024 pixels.

The comb mask polygon has 512 teeth (0.5 units wide with 0.5-unit gaps).
After the 2× scale: each tooth = 1px, each gap = 1px → 1024px total.
The XOR of solid mask ⊕ comb mask produces [0, 255, 0, 255, ...] × 512 pairs.

## Steps to Reproduce

### 1. Generate the PoC sticker
    python3 gen_poc_v3.py --out poc_v3.tgs --json poc_v3.json

This produces a valid Lottie animation (gzipped, <64KB) that passes Telegram
server-side validation checks.

### 2. Confirm the overflow with AddressSanitizer
Build Telegram Desktop (tested: v6.6.4 beta, commit 06c5154e99) with -fsanitize=address.
Or build the standalone reproducer:

    g++ -std=c++17 -g -O0 -fsanitize=address -o repro_asan repro.cpp
    ./repro_asan

Expected ASan output:
    ERROR: AddressSanitizer: stack-buffer-overflow on address ...
    WRITE of size 2 at offset 3266 in frame rleOpGeneric
    [1216, 3264) 'temp' (line 617) <== Memory access at offset 3266 overflows this variable

### 3. Confirm RIP (return address) control
    g++ -O0 -fno-stack-protector -no-pie -o rip_control rip_control.cpp
    ./rip_control

Expected output:
    SIGSEGV. return address overwritten
    rip = 0x00000000004013f7
    rbp = 0x00ff000141410205

The attacker-chosen marker value (y=0x4141) appears in the corrupted registers,
proving the overflow writes attacker-influenced data into control-flow-critical
stack slots.

### 4. Confirm arbitrary code execution (system() call)
    g++ -O0 -fno-stack-protector -no-pie -o exploit_system exploit_system.cpp
    ./exploit_system

Expected output:
    EXPLOITED — Arbitrary code execution achieved
    Executing: system("echo hello world")
    hello world

This demonstrates the complete exploit chain: overflow → RIP hijack → system() execution.

### 5. Send the sticker to a Telegram client
Send poc_v3.tgs to a target running a debug/ASan build. On receipt, the sticker
auto-plays and the overflow triggers immediately without user interaction.

## Technical Deep Dive: VRle::Span Struct Constraints

The overflow writes VRle::Span structs (not arbitrary bytes) past the buffer.
Each Span is 8 bytes with constrained fields:

    struct Span {          // offset  control
        short  x;          // [0:1]   fully controlled (mask X position)
        short  y;          // [2:3]   controlled (scanline number, same for all spans on a row)
        ushort len;        // [4:5]   fully controlled (mask gap width)
        uchar  coverage;   // [6]     controlled (mask opacity, range 1–255)
        uchar  padding;    // [7]     always 0x00
    };

The attacker controls span values through the Lottie mask geometry:
  - x:        mask path X coordinates (arbitrary positioning)
  - y:        scanline number (which row is being rendered)
  - len:      distance between coverage transitions (mask gap width)
  - coverage: pixel intensity from the mask rasterizer (1–255)

### Alignment Analysis: GCC vs Clang

The exploitability of the overflow depends critically on how the Span struct fields
align with the saved return address (RIP) on the stack. This alignment varies by
compiler.

Verified from real rleOpGeneric disassembly:

    ┌──────────┬──────────────┬──────────────┬────────────────────────────────────┐
    │ Compiler │ temp offset  │ Misalignment │ RIP Exploitability                 │
    ├──────────┼──────────────┼──────────────┼────────────────────────────────────┤
    │ GCC      │ RBP - 0x860  │ 0 bytes      │ Coverage byte lands on RIP byte 6  │
    │          │              │              │ → blocks canonical addresses       │
    ├──────────┼──────────────┼──────────────┼────────────────────────────────────┤
    │ Clang    │ RBP - 0x83c  │ 4 bytes      │ Coverage byte lands on RIP byte 2  │
    │          │              │              │ → canonical addresses possible     │
    └──────────┴──────────────┴──────────────┴────────────────────────────────────┘

**GCC builds (misalignment = 0):**
With 0-byte misalignment, each Span aligns perfectly with 8-byte stack slots.
The coverage field (byte 6, always 1–255) maps to bit 48+ of the return address.
All canonical x86-64 userspace addresses require bits 48–63 = 0. Coverage > 0
forces a non-canonical address → General Protection fault (#GP) → crash.

Direct RIP-to-address composition is blocked. However:
  - Denial of Service is 100% reliable (crash on every render)
  - The global-pointer-patch technique (demonstrated in exploit_system.cpp)
    can still redirect execution by writing the target address through a
    global pointer that survives the stack corruption

**Clang builds (misalignment = 4, typical for macOS Telegram):**
With 4-byte misalignment, Span fields map to RIP bytes as:

    RIP byte 0–1 = span.len      (fully controlled, 1–1024)
    RIP byte 2   = span.coverage  (controlled, 1–255)
    RIP byte 3   = span.padding   (always 0x00)
    RIP byte 4–5 = next_span.x    (controlled, depends on buffer position)
    RIP byte 6–7 = next_span.y    (controlled, scanline number)

This mapping is compatible with canonical addresses:
  - Byte 3 = 0x00 (padding) matches the zero byte required in code addresses
  - Byte 6–7 = scanline (can be 0 for addresses < 0x10000000000)
  - Coverage (byte 2) can represent any value 1–255

The remaining constraint is that next_span.x depends on the span's position
in the buffer (~530+ for typical overflow depth), making the composed address
very large (~2TB). This requires either:
  - mmap() of executable code at the large address (theoretical)
  - Negative offsetX to reduce x values (reduces available spans)
  - Multi-scanline attack (different y per pass)

## Impact Assessment

### Confirmed
- **Zero-click crash (DoS):** 100% reliable on all builds. Any crafted sticker
  with the dual-mask/2x-scale pattern crashes the Telegram client on render.
  No user interaction required — stickers auto-play.

- **Return address overwrite:** Confirmed via rip_control.cpp. The saved RIP is
  overwritten with attacker-influenced Span data.

- **Code execution (PoC):** Confirmed via exploit_system.cpp. The overflow
  redirects execution to system("echo hello world"), demonstrating arbitrary
  command execution from the vulnerable code path.

### Theoretical (requires additional work for in-the-wild exploitation)
- ASLR bypass (info leak or brute-force, typical for browser-class exploits)
- Stack canary bypass (not present in all builds; rlottie bundled code may
  be compiled without -fstack-protector depending on build configuration)
- ROP chain construction for builds where direct address composition is blocked
- Reliable Telegram server validation bypass (current PoC passes basic checks)

## Suggested Fix
Add an output capacity parameter to `bufferToRle()` and enforce bounds:

    size_t bufferToRle(uchar *buffer, int bufferLen, int size,
                       int offsetX, int y, Span *out, size_t outCapacity)
    {
        // ... existing code ...
        if (count >= outCapacity) return count;  // prevent overflow
        // ...
    }
