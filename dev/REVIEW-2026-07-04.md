## Findings

### F3 — [HEADLINE] Ships libheif v1.21.2 with a known 0-click heap-overflow-write (CVE-2026-32740, CVSS 8.8) — reachable, fixed by pin bump
The app pins **libheif v1.21.2** (`Telegram/build/prepare/prepare.py:969`,
`Telegram/build/docker/centos_env/Dockerfile:292`). That version has
**CVE-2026-32740** (CVSS **8.8**, published 2026-05-19): a heap-buffer-overflow **write** in
`HeifPixelImage::copy_image_to()` (`libheif/pixelimage.cc:1207`). A HEIF file with a **1×4 grid
of odd-height tiles** (YCbCr 4:2:0) makes the chroma-plane offset and copy-height diverge (each
computed with independent ceiling division), writing **64 bytes of fully attacker-controlled
chroma data past a heap allocation**. Per the advisory it "is triggered during normal image
decoding with default build settings"; any app decoding grid HEIF/AVIF is affected → potential
RCE via heap grooming.
- **Our exposure:** `HEIFPlugin` is statically imported unconditionally
  (`cmake/.../kimageformats/init.cpp`) and QImageReader **content-sniffs** (`HEIFHandler::canRead`
  matches the `ftyp` box), so a `.heic`/HEIF blob is routed to `heif.cpp` →
  `heif_decode_image(handle, …, heif_colorspace_RGB, heif_chroma_interleaved_*, …)`, which drives
  the grid-tile chroma compositing path. Grid tiling is the standard iPhone HEIC layout.
- **0-click vector:** a malicious HEIF **document/file** (mime `image/heic`) or sticker that
  carries original bytes → auto thumbnail/preview decode. (Photos are typically server-transcoded
  to JPEG; the document/sticker path is the honest 0-click lead — same file→gate→decoder
  discipline as the rlottie work.)
- **libheif v1.21.2 also carries** (all fixed by 1.22.0/1.22.1, several 0-click on the same
  decode path): CVE-2026-32741 (mask-image OOB write — needs `mski` item, low reach),
  CVE-2026-47254 (Track sample OOB — animated HEIF), CVE-2026-48029 (irot/grid OOB read),
  CVE-2026-47178 (unci OOB write), integer overflows CVE-2026-47714/32738/32739, plus 1.22.1's
  GHSA-5hqq (inline-mask OOB write) / GHSA-r7qj (icef OOB read).
- **libavif is pinned v1.3.0 — clean** for CVE-2025-48174/48175 (fixed *in* 1.3.0). libjxl v0.11.2
  matches the system copy; no outstanding CVE found this pass.
- **Fix applied:** bumped the libheif pin to **v1.22.2** (latest; all of the above) in both build
  manifests (`prepare.py`, `centos_env/Dockerfile`).
- **PoC — CONFIRMED end-to-end** (`dev/kimg-fuzz/cve-2026-32740/`, 845-byte `poc_grid.heic`,
  `asan_trace.txt`). Built libheif **v1.21.2** under clang+ASan, drove the vendored `heif.cpp`
  wrapper via the file driver `drv_heif_clang`:
  ```
  ==ERROR: AddressSanitizer: heap-buffer-overflow ... WRITE of size 64
    #1 HeifPixelImage::copy_image_to()          pixelimage.cc:964
    #2 ImageItem_Grid::decode_and_paste_tile_image  grid.cc:564
    ...
    #17 HEIFHandler::ensureDecoder()            heif.cpp:525   <-- OUR wrapper
    #18 HEIFHandler::ensureParsed()             heif.cpp:429
  0x... is located 0 bytes after 16143-byte region   <-- 64-byte OOB heap WRITE
  ```
  The overflow is reached through **our exact delivery glue** — `HEIFHandler::ensureDecoder`
  → `heif_decode_image` → grid-tile chroma compositing. PoC geometry: 1×4 grid of 63×63
  (odd-height) tiles, 4:2:0.
- **Fix VERIFIED:** rebuilt the *same wrapper* against **v1.22.2** (compiles unchanged — API
  compatible, resolving the earlier build-compat concern) and re-ran the identical PoC:
  decodes cleanly to a valid `63×252` image, **no ASan error**; the valid seed still decodes
  (`24×24`) — no regression. The pin bump concretely closes the bug on our path.

### F1 — MTProto pre-auth out-of-bounds heap read (CONFIRMED, fixed, repro) — CWE-125
`Telegram/SourceFiles/mtproto/connection_abstract.cpp:141` (`parseNotSecureResponse`).
`answerLen` is a **byte** length (written `<< 2` in `prepareNotSecurePacket`, bounds-checked
against `(len-5)*sizeof(mtpPrime)` bytes) but was passed to `gsl::make_span(answer+5, answerLen)`
as an **mtpPrime element** count. The span — and the `end` pointer both callers derive from it
(`readPQFakeReply`, `DcKeyCreator::readNotSecureResponse`) — reaches up to 4x past the packet
allocation, so the TL deserializer reads off the heap.
- **Reachable:** malicious/MITM server or MTProto proxy, pre-auth (fake `req_pq` on every
  TCP/HTTP connect, and the whole DH key-creation exchange).
- **Impact:** OOB heap read → remote crash/DoS at connection setup; low info-leak (over-read
  lands in `resPQ.pq`/fingerprints, not echoed). Upstream bug (2018) — affects official tdesktop.
- **Fix:** `gsl::make_span(answer + 5, answerLen / sizeof(mtpPrime))`. Behaviour-identical for
  valid traffic (`answerLen` is always a multiple of 4 == `(len-5)*4`).
- **Repro:** `dev/mtproto-notsecure-oob/` — ASan shows a 1596-byte read 0 bytes past a 420-byte
  region on the buggy version; clean after fix.

### F2 — MTProto FakeTLS ServerHello short-length abort (CONFIRMED, fixed) — CWE-125 / reachable abort
`Telegram/SourceFiles/mtproto/details/mtproto_tls_socket.cpp:756` (`checkHelloDigest`).
The FakeTLS ServerHello length fields (`part2Size`, `part4Size`) are fully attacker-controlled;
nothing enforces a minimum. With both = 0, `_serverHelloLength` = 16 and the code computes
`fulldata.subspan(43, 32)` over a 48-byte span → GSL `Expects` violation → `std::terminate`
(the digest is extracted *before* the HMAC check, so no secret knowledge is needed). If GSL
contracts were disabled it would be a 32-byte OOB read + zero-write (`set_with_const`).
- **Reachable:** malicious FakeTLS MTProto proxy (secret `0xEE…`, user-configured/semi-trusted)
  or a MITM on the TLS-looking TCP stream, pre-auth. Niche (only when a FakeTLS proxy is used).
- **Impact:** remote client abort (DoS) at connect. Upstream code.
- **Fix:** reject `_serverHelloLength < kServerHelloDigestPosition + kHelloDigestLength` (43)
  before the subspan.

## §3 — Image decoders (top-priority area): harness + results

System has libavif 1.4.1 / libheif 1.22.0 / libjxl 0.11.2 + Qt6 6.11.1 dev. Shipped app pins
libavif **v1.3.0**, libheif **v1.21.2**, libjxl **v0.11.2** (jxl matches exactly). The wrapper
glue is vendored (`kimageformats` v5.116.0) and identical regardless of lib version.

**Harness** (`dev/kimg-fuzz/`): compiles each vendored `QImageIOHandler` wrapper against system
libs under libFuzzer+ASan(+UBSan) and drives `handler->read()` on fuzzed bytes — the same call
Qt's plugin path makes. Per-format binaries (`fuzz_qoi/avif/heif/jxl`) to avoid plugin-symbol
collisions.

**Results (campaign, 900s each):** AVIF ~330k+ execs, JXL ~214k+, QOI ~23k — **no crashes**.
(final numbers appended below.)

**HEIF caveat:** libheif is C++ with RTTI; an ASan-instrumented harness linking a
non-instrumented libheif crashes in `__dynamic_cast` on *valid* input (verified: the real
`heif-dec` CLI and a non-sanitized build of the same wrapper both decode the seed fine). This is
a sanitizer×RTTI-interposition false positive, not a bug. libavif/libjxl expose C APIs and fuzz
cleanly. HEIF was reviewed statically instead.

**Static review of the decode glue — all memory-safe:**
- **QOI** (`qoi.cpp`, hand-written, imported unconditionally): the unchecked multi-byte
  `QOI_OP_RGB/RGBA/LUMA` reads are covered by the 8-byte `QOI_END_STREAM_PAD` slack (max 4-byte
  over-read); dims capped 300000², `px_len`/`imageAlloc` gated. Clean.
- **AVIF** (`avif.cpp`): decode delegates to libavif; output buffer sized from the decoder's own
  dimensions; 65535 + 256MP + `imageDimensionLimit` guards; CLAP/IROT/IMIR are bounds-clamped
  Qt ops. Clean glue.
- **JXL** (`jxl.cpp`): `align=0` tightly-packed `m_buffer_size` (4·w·h / 8·w·h) exactly matches
  the RGBA8888/RGBA64 QImage stride (no scanline padding for those formats); null-checked
  `imageAlloc`; 65535 + 256MP guards. Clean glue.
- **HEIF** (`heif.cpp`): plane→QImage copy uses the decoded image's own w/h for both the
  `imageAlloc` and the loop bounds (consistent), `stride` from libheif, alloc-gated. Clean glue.

**Reachability note:** the static plugins are imported unconditionally
(`cmake/.../kimageformats/init.cpp`) and QImageReader **content-sniffs** (each wrapper's
`canRead` peeks the magic), so the decoder is chosen by attacker-crafted header bytes regardless
of file extension/MIME — 0-click on receipt for document/sticker paths that carry original bytes.
(`App::readImage`/`app.h` are not present in this fork branch's tree — untracked/mid-refactor —
so the exact delivery body couldn't be walked here; plugin enablement is confirmed.)

**Bottom line for §3:** the tdesktop-side glue is hardened; residual risk is inside the vendored
C/C++ libs (OSS-Fuzz'd upstream). No novel glue bug found in the fuzzing budget. Highest-ROI
next step is version-vs-CVE on the *pinned* libheif v1.21.2 / libavif v1.3.0 (see TODO).
